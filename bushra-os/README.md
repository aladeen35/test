# نظام البشرى لإدارة الشركة — AI-Bushra Company OS

نسخة أولية قابلة للتجربة من النظام الإداري الموصوف في [`docs/SPEC.md`](docs/SPEC.md) لشركة **البشرى للتكنولوجيا – AI-Bushra Technology**.
تطبيق ويب تقدّمي (PWA) بالعربية، يعمل دون خادم، ويحفظ البيانات في متصفح الجهاز.

## ▶️ التشغيل

```bash
cd bushra-os
python3 -m http.server 8080
# ثم افتح http://localhost:8080
```

عند أول فتح يظهر **معالج الإعداد الأولي**: بيانات الشركة ← الهوية البصرية ← المدير العام ← الأقسام والمناصب ← الوحدات وحد اعتماد المدير العام ← الأمان والفريق.
اختيار «فريق تجريبي» يملأ كل المناصب الـ 22 بموظفين حتى تجرّب مسارات الموافقة فوراً. للدخول بأي موظف: سجّل الخروج من شارة المستخدم ثم اختره.
المناصب الحساسة (المدير العام، المالية، الموارد البشرية، الأمن) تطلب رمز تحقق يظهر في إشعار **على سبيل المحاكاة**.

### المرحلة الثالثة: المشاريع والإنتاج والجودة

| الوحدة | ما يعمل الآن |
|---|---|
| **المشاريع** | دورة حياة كاملة بعشر مراحل (مسودة ← … ← مغلق)، والانتقال للمرحلة التالية فقط مع موانع آلية لكل مرحلة. لا يُعتمد المشروع دون عقد معتمد أو عرض سعر وافق عليه العميل. يتضمن مراحل التسليم، والمخاطر، ومحاضر الاجتماعات، وطلبات تغيير النطاق عبر مسار موافقة يحدّث الميزانية والموعد عند اكتماله |
| **المهام** | لوحة مهام لكل مهمة فيها منفذ ومراجع مختلف ومعيار قبول. **لا تنتقل المهمة إلى «مكتملة» إلا بعد أن يتحقق المراجع من المعيار**، ولا يستطيع المنفذ إقفال مهمته. تسجيل الساعات وعدّاد إعادة العمل |
| **الاختبار** | حالات اختبار مرتبطة بالمهام والمتطلبات، ونتائج ناجح/فاشل/محجوب مع المنصة والجهاز والإصدار والدليل. **الفشل ينشئ عيباً تلقائياً**. العيب «المُصلح» يُغلق بنجاح إعادة الاختبار ويُعاد فتحه عند فشلها. يشمل اختبار قبول المستخدم وتقرير جاهزية الإطلاق |
| **الجودة** | قوائم فحص موحدة: بوابة الجودة، مراجعة مستند، مراجعة كود، مراجعة تصميم. بنود البوابة تُحسب آلياً من البيانات على الإصدار الحالي. **استقلال الجودة**: لا يراجع مدير المشروع أو المنفذون عملهم. **بوابة الجودة لا يتجاوزها حتى المدير العام**. تقارير عدم المطابقة بإجراءات تصحيحية ووقائية، والتحقق من الفعالية يتم بغير مالك الإجراء |
| **التسليم والإطلاق** | محضر تسليم مطبوع بالهوية، وطلب إطلاق يمر بمسار القسم 7.2، وتقرير ما بعد الإطلاق قبل إغلاق المشروع |
| **خدمة العملاء والدعم** | تابعة لمدير الجودة، بمسار القسم 6.7 (استقبال ← … ← تحليل جودة) واتفاقية مستوى خدمة لكل أولوية مع تنبيه وتسجيل عند التجاوز. **لا تُغلق التذكرة بإرسال رد**: الإغلاق يحتاج تأكيد العميل أو نتيجة موثقة أو قرار تصعيد يعتمده مدير الجودة، مع سبب جذري إلزامي. يتبعه قياس رضا العميل. يمكن تحويل التذكرة إلى عيب أو شكوى عالية الخطورة أو إجراء تصحيحي، والرد من قاعدة معرفة معتمدة |
| **صوت العميل والمؤشرات** | تحليل الأسباب المتكررة وفتح إجراء تصحيحي منها، وتقرير أسبوعي للجودة وخدمة العملاء، ومؤشرات القسم 11 في لوحة المدير العام: التسليم في الموعد، والعيوب بعد الإطلاق، والرضا، واتفاقية الخدمة، وزمن الإصلاح، واجتياز البوابة |

### المرحلة الرابعة: الموارد البشرية والعلاقات

| الوحدة | ما يعمل الآن |
|---|---|
| **ملف الموظف الموحد** | يضم العقد بإصداراته، والحضور، والأهداف والتقييم، والعهد، والمهارات والتدريب، وخطة التأهيل أو إنهاء الخدمة، والملف السري. **كل قسم حساس يظهر لمن يحتاجه فقط**: العقد والأجر للموظف والموارد البشرية، والأهداف والتقييم للموظف ومديره المباشر، والملاحظات السرية والجزاءات للموارد البشرية والمدير العام فقط (ولا تُكتب تفاصيلها في سجل التدقيق العام). مدير المشروع يرى الحد الأدنى |
| **الحضور** | تسجيل الحضور والانصراف من الرئيسية، مع التأخر حسب الدوام وفترة السماح، والعمل عن بعد، ورصد الغياب آلياً وتنبيه المدير المباشر. الإجازة المعتمدة تُسجل تلقائياً، ويُنبَّه الموظف ومديره عند اقتراب نفاد الرصيد. التصحيح للموارد البشرية بسبب مكتوب |
| **الأداء** | أهداف بأوزان لا يتجاوز مجموعها 100%، وتقييم بخمسة معايير يعرض للمقيّم مؤشرات موضوعية (إعادة العمل، والعيوب المعاد فتحها، والغياب، والتأخر). المسار: المدير المباشر ← اطلاع الموظف وتعليقه ← اعتماد الموارد البشرية، ولا يعتمد المقيّم تقييمه |
| **العهد والأصول** | سجل أصول وتسليم واستلام بتوثيق للفقد والتلف. **الأصل المشترى عبر «طلب شراء» يُسجل تلقائياً عهدة لطالب الشراء** عند إغلاق الطلب |
| **التأهيل وإنهاء الخدمة** | خطة 30/60/90 يوماً تُنشأ تلقائياً عند دعوة موظف، مع تنبيه مديره ومدير التدريب. إيقاف الحساب يفتح قائمة إنهاء خدمة تضم كل عهدة مسجلة، وبند العهدة لا يُقفل إلا باستلام الأصل |
| **التدريب والتطوير** | كتالوج مهارات ومصفوفة المستوى المطلوب لكل منصب. تحليل فجوات مرتب بحسب حجم الفجوة ومؤشرات التقييم وإعادة العمل والعيوب وشكاوى العملاء. البرامج تمر بالحالات الثماني، والاعتماد عبر مسار «خطة / طلب تدريب» (يمر بالمالية عند وجود تكلفة، وبالجودة عند ارتباطه بعيب). **لا يكتمل البرنامج بمجرد الحضور**: يلزم تقييم قبلي وبعدي ونتيجة وتسجيل الأثر. عند الاكتمال تُحدَّث مصفوفة مهارات الناجحين وتُصدر شهادات بصلاحية، ويُنبَّه قبل انتهائها. يشمل سجل المدربين والمزودين وتقييمهم |
| **العلاقات العامة والمحتوى** | تقويم نشر شهري، ومحتوى يمر بمسار «نشر إعلامي». **لا يُرسل للاعتماد، ولا يُنشر، محتوى يذكر عميلاً دون موافقة موثقة**، وسحب الموافقة يوقف النشر وينبه مسؤول العلاقات العامة. يشمل مكتبة الهوية مع قواعد الاستخدام (الختم مقيد) |
| **صفحة العميل** | سجل التواصل والاجتماعات والخطوات التالية، وسجل موافقة النشر بمصدرها ونطاقها، واستبيانات الرضا وصافي التوصية (NPS)، والمشاريع والعروض والفواتير والتذاكر والشكاوى في مكان واحد |

### المرحلة الخامسة: الحماية والتوسع

| الوحدة | ما يعمل الآن |
|---|---|
| **سجل معالجة البيانات** | لكل نشاط: نوع البيانات، والغرض، والمصدر، والمتلقي، ومكان التخزين، ومدة الاحتفاظ، والأساس النظامي، والتصنيف، والمالك. يطابق أعمدة ورقة «معالجة البيانات» في سجلات الشركة. يشمل تصنيف فئات البيانات ومن يطّلع عليها |
| **طلبات أصحاب البيانات** | اطلاع، وتصحيح، وحذف، واعتراض، بمهلة نظامية وتنبيه عند التأخر. **لا تُسلَّم البيانات ولا تُصحح قبل التحقق من الهوية**. نسخة البيانات تُجمع آلياً من كل الوحدات. **الحذف إخفاء هوية** يقترحه شخص ويعتمده آخر (المراجع القانوني أو المدير العام)، بعد فحص موانع (موظف على رأس العمل، عهد، فواتير مفتوحة)، مع الاحتفاظ بما يلزم نظاماً. لا يُكتب اسم صاحب البيانات في سجل التدقيق |
| **خطة الاستجابة للحوادث** | ست خطوات لكل حادث أمني: الاحتواء، التقييم، الإزالة، الاستعادة، قرار الإبلاغ، الدروس المستفادة. **لا يُغلق الحادث في محرك الموافقات قبل اكتمال الخطة**، وقبل توثيق قرار الإبلاغ إن مسّ بيانات شخصية |
| **النسخ الاحتياطي** | نسخة مشفرة AES-256-GCM بعبارة يختارها المسؤول (مفتاح مشتق بـ PBKDF2)، مع بصمة SHA-256 للمحتوى. **اختبار استعادة** يفك التشفير ويتحقق من البصمة ومن سلسلة التدقيق كاملة دون المساس بالبيانات الحالية. الاستعادة الفعلية للمدير العام فقط. تنبيه عند تجاوز سياسة النسخ |
| **مراجعة الصلاحيات** | مراجعة دورية تعرض لكل حساب آخر دخول وملاحظات (غير نشط، صلاحية منتهية، سرية أعلى من المعتاد، صلاحية إدارة). القرار إبقاء أو سحب بسبب، ولا تُغلق المراجعة قبل البت في كل حساب. السحب يوقف الحساب فوراً ويفتح قائمة تسليم العهد |
| **سجلات الأمان** | الدخول والخروج، والمحاولات الفاشلة، والوصول المرفوض، وتغيير الصلاحيات، والتصدير والتنزيل، مع كشف الأنماط الشاذة (محاولات فاشلة متكررة، قفل حسابات، تنزيل بكميات كبيرة) |
| **كلمات المرور المحلية** | اختيارية من إعدادات الأمن. يعيّن كل مستخدم كلمة مروره عند أول دخول، وتُحفظ بصمتها فقط (PBKDF2-SHA256، 150 ألف تكرار مع ملح). يُقفل الحساب بعد محاولات فاشلة، وإعادة التعيين للموارد البشرية أو الأمن. تليها المصادقة متعددة العوامل للمناصب الحساسة |
| **التكاملات** | **البريد**: صندوق صادر يجهز رسالة لكل إشعار، والرسائل السرية بعنوان عام دون تفاصيل مع رابط آمن (القسم 10). **الدفع**: مرجع دفع برقم تحقق على كل فاتورة مع بيانات الحساب. **التوقيع**: توقيع بخط اليد على الشاشة لإصدار محدد من مستند أو محضر تسليم، مربوط ببصمة المحتوى، فيظهر عدم التطابق عند أي تعديل |
| **الجوال** | شريط تنقل سفلي على الشاشات الصغيرة، وزر «تثبيت التطبيق» في قائمة الحساب |

البيانات المحفوظة من الإصدار السابق تُرقّى تلقائياً عند الفتح: تُضاف الوحدات الجديدة وصلاحياتها ومسار «تغيير النطاق» دون المساس بما سبق.

اختبارات القبول الأولية في القسم 14 نُفذت آلياً في متصفح Chromium، وكلها تعمل: التسلسل الوظيفي، دعوة موظف، عرض سعر ← فاتورة، طلب شراء عبر موافقات متعددة، إجازة واعتمادها، تقييد الحادث الأمني، إصدار جديد بعد الاعتماد، تعطيل موظف، وتقرير التدقيق.

## ⚠️ حدود النسخة الأولية

- **لا يوجد خادم ولا مصادقة حقيقية.** البيانات في `localStorage` لجهاز واحد، والدخول باختيار المستخدم، ورمز MFA محاكاة. التشغيل الفعلي يحتاج خادماً وقاعدة بيانات ومصادقة وتشفيراً، وهذا ما يقصده القسم 14 من المواصفات: قرار الاستضافة يسبق التنفيذ الكامل.
- بصمة التدقيق (cyrb53) تكشف التعديل العرضي، لكنها ليست توقيعاً تشفيرياً. في الإنتاج يُحفظ السجل على الخادم مع توقيع.
- الإرسال الفعلي للبريد، وربط بوابة الدفع، والتوقيع المعتمد رسمياً، كلها تتطلب خادماً ومزودين يُختارون بعد تحديد الحاجة (القسم 15). النظام يجهز البيانات لها.
- الحضور يعتمد على تسجيل الموظف في المتصفح، ولا يوجد ربط بجهاز بصمة.
- قوالب الحزمة مسودات فيها حقول «يُعبأ». لا تُوقّع قبل مراجعة محامٍ أو مستشار مرخّص في السودان.
